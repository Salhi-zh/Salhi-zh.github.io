Use-after-free noyau → root : nft_tunnel (lab)

2026 Linux 6.1 · Debian 12 · KASAN gdb · pwndbg lab

Un objet libéré sans relâcher ses références laisse des pointeurs pendants dans des SKB parkés. En transformant ce use-after-free en écriture contrôlée du chemin ->destroy, j'ai obtenu un shell root reproductible — le tout dans une VM d'entraînement instrumentée.

Cadre Travail d'exploitation en laboratoire (VM dédiée, noyau compilé avec KASAN), à but d'apprentissage de la sécurité noyau. Objectif : comprendre la mécanique d'un UAF réel de bout en bout — pas de cible de production, pas de 0-day revendiqué.

01 Le bug

Dans la destruction d'un objet tunnel de nftables, la routine libère une structure metadata_dst via kfree() sans passer par dst_release(). Résultat : le compteur de références n'est jamais décrémenté proprement, et des SKB déjà parkés (côté TUN) conservent des références vers une zone désormais libre.

// schéma du défaut
nft_tunnel_obj_destroy():
    kfree(metadata_dst)   // libère…
    // …mais dst_release() manquant → refs pendantes dans les SKB parkés

On a donc une fenêtre classique : mémoire libérée mais encore atteignable via un autre chemin (la lecture des paquets parkés).

02 Chaîne d'exploitation

Créer un objet tunnel NFT → allocation de metadata_dst.
Émettre un paquet : le hook NF_NETDEV_EGRESS parke le SKB dans l'anneau TUN, référence du dst conservée.
Cascade DELTABLE → kfree(metadata_dst) : déclenchement du UAF.
Drainer la quarantaine : ~700K cycles alloc/free pour vider la mise en quarantaine.
Spray : 512 objets contrôlés dans kmalloc-cg-256 pour réoccuper la zone libérée.
Lecture TUN → dst_release → call_rcu → dst_destroy → appel de ops->destroy.
ops->destroy pointé sur commit_creds → uid = 0.
Shell root reproductible.

03 Le point de bascule

La première approche visait un gadget exec_work, mais elle exigeait un chemin valide, bloqué par msg->security = NULL. Le déblocage a été de rediriger la primitive vers l'appel de destruction RCU et de pointer ops->destroy directement sur commit_creds :

// réoccupation : ops->destroy contrôlé
ops->destroy = 0xffffffff81233940   // commit_creds
// appelé via dst_destroy sous call_rcu → escalade des credentials
Résultat uid=0 — shell root reproductible (Linux 6.1.170-kasan)

04 Ce que KASAN a appris

Compiler le noyau avec KASAN a été décisif : chaque accès pendant transformait un crash opaque en rapport précis (adresse, taille, timeline alloc/free). L'exploitation noyau, c'est autant de la lecture de logs d'instrumentation que de l'écriture d'exploit.

  • Grooming du tas : comprendre la quarantaine (le free ne rend pas la zone immédiatement réutilisable) et la drainer avant le spray.
  • Choix du cache : viser le bon slab (kmalloc-cg-256) pour que l'objet de spray recouvre la victime.
  • Sélection de gadget : pivoter d'un chemin bloqué (contrainte security) vers un chemin RCU exploitable.
  • Discipline : notes itératives des impasses (approche exec_work, callbacks RCU bloqués…) — l'historique des échecs est la solution.
Prise de recul défensive Deux mitigations auraient cassé la chaîne : (1) l'appariement correct alloc/dst_release (le fix du bug lui-même), (2) le durcissement du slab / la randomisation du freelist qui rendent le spring déterministe bien plus dur. C'est exactement la valeur de l'exercice offensif : voir où placer la défense.
