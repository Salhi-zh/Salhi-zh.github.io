Use-after-free noyau → root : nft_tunnel (lab)

2026 Linux 6.1 · Debian 12 · KASAN gdb · pwndbg · C n-day · CVE-2022-32946 lab

Reproduction documentée d'un n-day connu : un objet libéré sans relâcher ses références laisse des pointeurs pendants dans des SKB parkés. En transformant ce use-after-free en écriture contrôlée du chemin ->destroy, j'ai obtenu un shell root reproductible — après trois approches échouées, 16 notes d'itération, et un pivot de gadget que rien ne garantissait. Le tout dans une VM d'entraînement instrumentée.

Cadre Reproduction d'un n-day connu (CVE-2022-32946), pas une découverte originale. Travail d'exploitation en laboratoire (VM QEMU dédiée, noyau Linux 6.1.170 compilé avec KASAN, KASLR désactivé pour le développement). Objectif : comprendre la mécanique d'un UAF réel de bout en bout — l'analyse du bug, la construction de l'exploit, et surtout les impasses — pas de cible de production, pas de 0-day revendiqué.

01 Le bug

Dans nft_tunnel_obj_destroy() (net/netfilter/nft_tunnel.c:697), la routine de destruction d'un objet tunnel NFT libère une structure metadata_dst via kfree() sans passer par dst_release() :

// net/netfilter/nft_tunnel.c — la ligne qui crée le bug
nft_tunnel_obj_destroy():
    metadata_dst_free(priv->md);   // → kfree() directement
    // dst_release() manquant → le compteur de références n'est jamais décrémenté

Quand un paquet traverse un hook NF_NETDEV_EGRESS, le noyau appelle nft_tunnel_obj_eval() qui fait dst_hold() puis skb_dst_set() — le SKB conserve une référence vers le metadata_dst. Si le paquet est parké dans un anneau TUN et qu'on détruit la table NFT entre-temps, le kfree() libère la mémoire alors que le SKB conserve un pointeur pendant.

Qu'est-ce qu'un use-after-free ?

La mémoire est libérée (free) mais encore atteignable par un autre chemin (use). Si un attaquant arrive à réoccuper la zone libérée avec des données contrôlées avant que le chemin pendant ne la relise, il contrôle ce que le noyau lit — et potentiellement ce qu'il exécute.

ÉtapeOpération noyauÉtat de metadata_dst
1NEWOBJ tunnel → metadata_dst_alloc()Alloué dans kmalloc-cg-256 (208 octets)
2nft_tunnel_obj_eval() → skb_dst_set()Référencé par le SKB parké dans TUN
3DELTABLE → kfree(metadata_dst)Libéré — mais le SKB conserve son pointeur
4Lecture TUN → dst_release()Accès à une zone déjà libérée → UAF

02 Topographie du noyau

Avant de construire quoi que ce soit, il faut cartographier les structures en mémoire. Ces offsets déterminent tout : où poser un faux pointeur, quelle valeur doit être nulle, quel champ contrôle le flux d'exécution.

dst_entry (include/net/dst.h)

// dispositions des champs critiques
+0x00  dev          // net_device*
+0x08  ops          // dst_ops* → contient le pointeur destroy
+0x20  xfrm         // DOIT être 0 sinon dst_destroy suit la chaîne xfrm
+0x40  __refcnt     // atomic_t — dst_release() décrémente ici
+0x58  rcu_head     // utilisé par call_rcu()

dst_ops (include/net/dst_ops.h)

+0x00  family
+0x08  gc
+0x30  destroy      // ← le pointeur de fonction qu'on détourne

Quand dst_release() décrémente __refcnt à zéro, le noyau appelle call_rcu(&dst->rcu_head, dst_destroy_rcu). Le callback RCU exécute dst_destroy(), qui lit dst->ops->destroy et l'appelle avec dst en argument :

// dst_destroy() — le chemin qui nous donne le contrôle (désassemblé)
ffffffff82729b28  mov 0x8(%rbx),%rbp     ; rbp = dst->ops
ffffffff82729b41  mov 0x30(%rbp),%rax    ; rax = ops->destroy
ffffffff82729b48  je  <skip>             ; saute si NULL
ffffffff82729b4a  mov %rbx,%rdi          ; rdi = &fake_dst (premier argument)
ffffffff82729b4d  call retpoline_rax     ; → appelle notre fonction cible

Si on contrôle ops->destroy, on contrôle rax — et donc l'exécution du noyau.

L'exploit démarre en espace utilisateur non privilégié et crée ses propres namespaces via unshare(). La table NFT, le device TUN, et toute la chaîne sont construits sans aucun privilège root — c'est ce qui rend cette classe de bugs dangereuse en pratique.

04 Première approche : exec_work

La stratégie initiale : faire en sorte que ops->destroy pointe vers call_usermodehelper_exec_work(), qui prend un subprocess_info* et appelle kernel_execve(path). Si on glisse "/tmp/lpe_root.sh" dans le champ path, le noyau exécute notre script en root.

Le plan

Créer un objet tunnel NFT → metadata_dst alloué dans kmalloc-cg-256.
Créer une chaîne NETDEV avec hook NF_NETDEV_EGRESS sur le TUN.
Envoyer un paquet UDP → le hook l'évalue, nft_tunnel_obj_eval() attache le dst au SKB, le TUN le parke.
DELTABLE cascade → kfree(metadata_dst) : le UAF est ouvert.
Drainer la quarantaine KASAN (~700 000 cycles alloc/free).
Spray : 512 messages msg_mm dans kmalloc-cg-256 — chacun contient un faux subprocess_info.
Lire le TUN → dst_release() sur le pointeur pendant → call_rcu → dst_destroy → ops->destroy().
call_usermodehelper_exec_work exécute /tmp/lpe_root.sh en root → chmod u+s /bin/bash.

Ce plan ne marchera pas. Voici pourquoi.

Impasse #1 — Constantes NFTA_ erronées Les constantes d'attributs Netlink étaient décalées de 1 par rapport aux enums du noyau : NFTA_TABLE_NAME à 2 au lieu de 1, NFTA_CHAIN_HOOK à 5 au lieu de 3, etc. (13 constantes fausses au total). Résultat : la chaîne et les règles étaient malformées, les paquets ne touchaient jamais la règle, nft_tunnel_obj_eval() n'était jamais appelé, et le dst n'était jamais attaché au SKB. Le UAF ne se déclenchait tout simplement pas. Diagnostic : dmesg affichait « attribute type 2 has an invalid length » trois fois par exécution.
Impasse #2 — Mauvaise méthode de spray Le spray initial utilisait pipe write(), qui stocke les données dans le page cache (pages de 4 Ko), pas dans kmalloc-256. La zone libérée n'était jamais remplie par nos données contrôlées. Correction : basculer vers msgsnd() avec un corps de 208 octets — kmalloc(sizeof(msg_msg) + 208, GFP_KERNEL_ACCOUNT) = 256 octets → même slab que metadata_dst.
Impasse #3 — path=NULL (fatale) Après correction des deux premiers bugs, le spray fonctionne et le TUN draine les paquets. Mais le script n'est jamais exécuté. Cause : le champ msg->security (offset 40 dans msg_mm) est fixé par les hooks LSM du noyau, pas par le payload userspace. Il est toujours NULL. Or subprocess_info->path est lu au même offset. Résultat : kernel_execve(NULL) → -EFAULT. Le kthread gagne brièvement root mais ne peut rien exécuter.

Tentative de contournement : basculer vers user_key_payload (add_key()) qui contrôle cet offset. Mais le quota de clés limite à ~96 créations sur 512 demandées — couverture de spray insuffisante. Impasse confirmée.

05 L'impasse — trois hypothèses, zéro succès

Avant de trouver la solution, j'ai passé du temps à comprendre pourquoi rien ne marchait. J'ai formulé trois hypothèses et conçu des tests pour les départager :

HypothèseDescriptionTestRésultat
H1 dst_release() n'est jamais appelé (le SKB utilise skb_dst_set_noref) Pas de moyen de vérifier sans instrumentation noyau Indéterminé
H2 Le callback RCU s'exécute dans ksoftirqd, pas dans le process enfant Placer 0xdeadbeef comme adresse cible → devrait provoquer un GPF visible si le callback se déclenche Pas de crash — soit le callback ne se déclenche pas, soit il crashe silencieusement dans un autre contexte
H3 Le UAF ne se déclenche pas (metadata_dst n'est pas réellement libéré) Vérifier les ACK de DELTABLE ACK reçu, mais pas de confirmation que le free a eu lieu

Test de force brute KASLR

Pour éliminer l'hypothèse que le problème soit simplement une mauvaise adresse à cause de KASLR, j'ai lancé un test exhaustif :

// brute-force : tester chaque slide KASLR possible
// CONFIG_PHYSICAL_ALIGN=0x200000 → 512 positions possibles
for k = 0 .. 287:
    fork() → exécuter l'exploit avec commit_creds + (k * 0x200000)
    if child exits(0) → root trouvé
// Résultat : 0 succès sur 287 essais (p < 0.000001)
// Conclusion : ce n'est PAS un problème de slide KASLR
Verdict 0/287 — le mécanisme lui-même est cassé, pas l'adresse

06 Le pivot : commit_creds direct

Le déclic est venu en reconsidérant la signature de l'appel. Quand dst_destroy appelle ops->destroy(dst), le premier argument (rdi) est l'adresse de notre objet de spray — un msg_mm. Si on pointe ops->destroy vers commit_creds() plutôt que exec_work, l'appel devient :

// au lieu de call_usermodehelper_exec_work(dst) ← a besoin d'un path valide
// on fait :
commit_creds((struct cred *)dst);   // dst = adresse de notre msg_mm

La différence cruciale :

GadgetExigencesRésultat
call_usermodehelper_exec_work Nécessite path valide à offset 40, argv valide, wait correct Bloqué — msg->security = NULL immutable
commit_creds Lit des champs d'une struct cred… mais ne valide pas strictement le format Fonctionne — même avec un argument qui n'est pas une vraie struct cred

commit_creds() prend un pointeur vers une struct cred et met à jour les credentials du processus courant. Même si notre msg_mm n'a pas la disposition d'un vrai cred, la fonction lit les champs nécessaires depuis la mémoire et modifie le uid/euid du processus courant à zéro.

Leçon Quand une chaîne de gadgets semble bloquée, chercher un gadget qui demande moins de pré-conditions. exec_work demandait un path valide que je ne pouvais pas fournir ; commit_creds était assez tolérant pour fonctionner avec des données partiellement valides. L'historique des échecs a créé la solution.

07 Chaîne d'exploitation finale

Namespaces : unshare(CLONE_NEWUSER | CLONE_NEWNET) — aucun sudo nécessaire. Mapping uid/gid via /proc/self/uid_map.
TUN device : ouvrir /dev/net/tun, configurer tun0 (10.0.0.1/24), l'activer, ajouter une route vers 10.0.0.0/24.
NEWTABLE + NEWOBJ : créer une table NFT NFPROTO_NETDEV et un objet tunnel (family=5, type=NFT_OBJECT_TUNNEL=6). L'allocation de metadata_dst a lieu ici : 208 octets → kmalloc-cg-256.
NEWCHAIN + NEWRULE : chaîne NETDEV avec hook NF_NETDEV_EGRESS sur tun0. Règle : expression objref (charge l'objet tunnel → appelle nft_tunnel_obj_eval() → dst_hold + skb_dst_set).
Paquet déclencheur : sendto() un datagramme UDP vers 10.0.0.2:9999 — le hook EGRESS l'évalue, attache le metadata_dst au SKB, et le TUN le parke dans son anneau.
DELTABLE : suppression en cascade de la table → nft_tunnel_obj_destroy() → kfree(metadata_dst). Le UAF est ouvert.
Drainage de quarantaine : ~700 000 cycles msgsnd/msgrcv pour vider la quarantaine KASAN et rendre la zone réallocable.
Spray : 512 messages msg_mm (8 queues × 64 messages) dans kmalloc-cg-256. Chaque message contient l'adresse de commit_creds répétée dans les champs critiques.
Drain TUN : lecture non-bloquante des paquets parkés → dst_release() sur le pointeur pendant → refcount à 0 → call_rcu(&dst->rcu_head, dst_destroy_rcu).
Callback RCU : dst_destroy() lit dst->ops->destroy = 0xffffffff81233940 = commit_creds. Appel : commit_creds(dst). Le processus courant gagne uid=0.
Shell root : getuid() == 0 → execl("/bin/bash", "bash", "-i", NULL).

Extrait du spray (C)

static void spray_direct_creds(void) {
    struct { long mtype; char data[208]; } mp = { .mtype = 1 };

    // Remplir les champs critiques avec l'adresse de commit_creds
    *(uint64_t *)(mp.data + 0)  = 0xffffffff81233940ULL; // commit_creds
    *(uint64_t *)(mp.data + 8)  = 0xffffffff83ef2b40ULL; // init_cred

    int sent = 0, qid[8];
    for (int q = 0; q < 8; q++) {
        qid[q] = msgget(IPC_PRIVATE, IPC_CREAT | 0600);
        for (int i = 0; i < 64; i++) {
            if (msgsnd(qid[q], &mp, 208, IPC_NOWAIT) < 0) break;
            sent++;
        }
    }
    // → 512 objets dans kmalloc-cg-256
}

08 Ce que KASAN a enseigné

Compiler le noyau avec KASAN (Kernel Address SANitizer) a été décisif. Chaque accès mémoire invalide est détecté et logué avec l'adresse fautive, la taille de l'accès, et la timeline alloc/free de l'objet. Sans KASAN, les bugs mémoire produisent des crashs opaques ou — pire — fonctionnent silencieusement. Avec KASAN, chaque erreur est une information exploitable.

  • Grooming du tas : KASAN met les objets libérés en quarantaine. Un kfree() ne rend pas immédiatement la zone réallocable — il faut drainer la quarantaine (~700K cycles) avant que le spray puisse occuper la zone.
  • Choix du cache : metadata_dst_alloc(0, METADATA_IP_TUNNEL, GFP_KERNEL_ACCOUNT) → 208 octets → kmalloc-cg-256. Le spray doit viser exactement le même slab, d'où msgsnd() avec 208 octets de payload (+ header msg_msg = 256).
  • dmesg_restrict : une complication non technique mais concrète — dmesg_restrict=1 empêche un utilisateur non-root de lire les logs KASAN via /dev/kmsg. J'ai dû relire les logs depuis la console QEMU.

09 Portabilité

La technique est intrinsèquement portable à tout noyau Linux 6.1.x contenant le bug nft_tunnel :

CouchePortable ?Ce qui change
VulnérabilitéOuiRien — même code noyau partout
Technique d'exploitationOuiRien — même sémantique TUN/NFT/RCU
Adresses des symbolesNonExtraire commit_creds depuis /proc/kallsyms ou vmlinuz

Une version « plug and play » auto-détecte l'adresse de commit_creds : d'abord via /proc/kallsyms (souvent masqué pour les non-root), puis en extrayant le payload xz de /boot/vmlinuz et en parsant la ksymtab de l'ELF résultant. Si KASLR est actif, le brute-force des 512 positions (CONFIG_PHYSICAL_ALIGN=0x200000) est envisageable.

11 Prise de recul défensive

L'intérêt de l'exercice offensif est de voir où placer la défense. Trois mitigations auraient cassé la chaîne :

MitigationÉtape bloquéeMécanisme
Appariement correct alloc/release Étape 6 (DELTABLE) Utiliser dst_release() au lieu de kfree() dans nft_tunnel_obj_destroy() — c'est le fix du bug lui-même. Pas de free sans que le refcount soit à zéro → pas de UAF.
Durcissement du slab (freelist randomization) Étape 8 (spray) Avec CONFIG_SLAB_FREELIST_RANDOM=y et CONFIG_SLAB_FREELIST_HARDENED=y, la réoccupation prédictible du slot libéré devient un exercice probabiliste plutôt que déterministe.
CFI (Control-Flow Integrity) Étape 10 (callback RCU) Avec CONFIG_CFI_CLANG=y, l'appel indirect via ops->destroy serait validé contre une table de cibles autorisées. commit_creds n'y figurerait pas → trap.
Principe La défense en profondeur fonctionne parce que chaque couche (correction du bug, durcissement de l'allocateur, intégrité du flux de contrôle) bloque une étape différente de la chaîne. Un attaquant doit contourner toutes les couches ; un défenseur n'a besoin d'en maintenir qu'une.

Bilan

  • Le bug : un kfree() sans dst_release() dans nft_tunnel_obj_destroy() — une erreur de référence-counting, la classe de bugs la plus commune du noyau Linux.
  • L'exploit : spray de msg_mm dans kmalloc-cg-256, drainage de quarantaine KASAN, détournement du callback RCU vers commit_creds.
  • Le pivot : trois approches échouées avant de trouver un gadget suffisamment tolérant. La solution n'est pas venue d'une inspiration mais de l'élimination méthodique des alternatives.
  • La discipline : documenter chaque impasse (16 notes, 1300 lignes) — parce que dans l'exploitation noyau, ce qui ne marche pas restreint l'espace de recherche autant que ce qui marche.
Divulgation CVE-2022-32946 est un bug connu et corrigé. Ce travail est une reproduction documentée à but éducatif, réalisée entièrement en environnement de laboratoire isolé. Aucune cible de production n'a été touchée.
