CTF & RE : ret2win, crackmes maison, lab anti-analyse & plateforme CTF

2026 Root-Me · PE32 / ELF64 IDA · Ghidra · gdb+pwndbg UPX · pwntools · FastAPI

Cinq angles de reverse et d'outillage : une exploitation binaire propre (ret2win) sur Root-Me, puis des crackmes que je concois puis casse — un license checker packe UPX a quatre couches de defense, un crackme XOR mono-octet a anti-debug ptrace, un laboratoire anti-analyse ou chaque detection est reactive (corruption de cle, pas simple exit) — et enfin le backend d'une plateforme CTF que j'ai bati et threat-modelise. Concevoir les defis et les resoudre.

Cadre & honnetete Le challenge Root-Me est un exercice public et autorise d'une plateforme d'entrainement. Les deux crackmes qui suivent sont des binaires que j'ai ecrits moi-meme — j'en possede le code source, donc le « ground truth » est verifiable — puis que je re-reverse a froid comme si je ne les connaissais pas. Concevoir des protections et les defaire dans un meme cycle est un exercice a double tranchant : on comprend une defense en la construisant, et on l'evalue en la cassant. Ce sont deux challenges soignes, pas une chaine d'usine.

01 Root-Me — Stack buffer overflow & ret2win

Challenge app-systeme-ch72 : un executable PE32 Windows x86 (ch72.exe), tournant sous Cygwin64 sur une machine Windows 10 (10.0.17763, hote challenge05). Il lit son entree avec une routine de type gets() dans un buffer de 16 octets, sans aucun controle de longueur. Objectif : lire $HOME/.passwd, un fichier appartenant a l'utilisateur app-systeme-ch72-crk et lisible uniquement par lui — alors que la session SSH tourne sous app-systeme-ch72.

ProtectionEtatConsequence
ASLROFFadresses statiques → on peut coder give_shell en dur
DEP / NXOFF(non necessaire ici — on ne fait pas de shellcode)
SafeSEHONecarte une exploitation par chaine SEH → on vise directement ret
Stack cookie (main)absentaucun canari a contourner sur la fonction vulnerable

Sans ASLR, sans cookie, et avec une fonction cadeau deja presente qui appelle system(), l'exploitation la plus propre est un ret2win : on n'injecte rien, on ecrase juste l'adresse de retour de main par celle de give_shell. SafeSEH etant ON, une exploitation par chaine SEH est ecartee — c'est le ret classique qui est le vecteur.

AdresseSymbole / role

; give_shell @ 0x401000 — la cible ret2win
0x401000  push  0x41b000       ; "C:\Windows\system32\cmd.exe"
0x401005  call  0x403bcc       ; system()
0x40100a  add   esp, 4          ; nettoie l'argument (convention cdecl)
0x40100d  ret

give_shell appelle system("cmd.exe"), ce qui lance un cmd.exe interactif heritant du stdin/stdout de l'appelant — exactement ce qu'il faut pour rejouer des commandes derriere l'exploit. Le add esp, 4 apres le call nettoie l'argument pousse sur la pile (convention cdecl : l'appelant nettoie la pile apres retour de la fonction appelee).

Layout de pile de main

; pile de main() — adresses hautes en haut
+------------------+
|  return address  |  ← cible : on ecrit ici 0x00401000
+------------------+
|   saved EBP      |  4 octets
+------------------+
|   counter        |  4 octets — compteur de la boucle toupper
+------------------+
|   buffer[16]     |  16 octets — l'entree commence ici
+------------------+
padding jusqu'a EIP = 16 + 4 + 4 = 24 octets

Le padding pour atteindre l'adresse de retour est donc de 24 octets : 16 (buffer) + 4 (counter) + 4 (saved EBP). Ensuite on place l'adresse de give_shell.

Comportement du lecteur d'entree

Le lecteur a 0x403f8c lit les octets un par un dans le buffer de pile sans aucune borne. Il s'arrete uniquement sur 0x0a (\n) ou 0xff. Les octets nuls (0x00) passent — ce qui est critique car l'adresse de retour 0x00401000 contient un null byte en poids fort. Apres lecture, main passe un toupper sur les 16 premiers octets seulement (le buffer declare), et le compteur est remis a 0 apres le debordement : les octets 16 a 27, dont notre adresse, ne sont jamais modifies.

Piege #1 — octet nul dans l'adresse L'adresse de retour 0x00401000 contient un octet nul en poids fort. Beaucoup de lecteurs s'arretent sur \0 — pas celui-ci. La boucle de lecture a 0x403f8c ne s'arrete que sur \n (0x0a) ou 0xff : les octets nuls passent. Toujours verifier la condition d'arret exacte du lecteur avant d'ecarter une adresse « a cause d'un null byte ».
Piege #2 — la boucle toupper ne couvre pas l'overflow Apres lecture, main passe un toupper sur les octets 0-15 seulement (le buffer declare), et son compteur est remis a 0 apres le debordement. Les octets 16-27 — dont notre adresse de retour — ne sont jamais mis en majuscule : l'adresse est preservee intacte. Une passe de « sanitisation » bornee au buffer declare est triviale a deborder ; il faut lire les bornes de boucle dans le desassemblage, pas les supposer.

Modele de privileges — la vraie difficulte

Ecraser EIP ne suffit pas : encore faut-il que le shell obtenu tourne avec le bon jeton d'acces. Le fichier n'est lisible que par -crk :

$ icacls .passwd
.passwd  CHALLENGE05\app-systeme-ch72-crk:(R)     ; lecture reservee
         NT AUTHORITY\SYSTEM:(F)
         BUILTIN\Administrators:(F)
$ type .passwd
Access is denied.                                ; sous app-systeme-ch72 → refuse

Root-Me fournit le mecanisme d'elevation classique : un wrapper.sh qui ouvre une session SSH sans mot de passe vers le compte -crk, dont le shell de connexion est precisement ch72.exe. En faisant passer l'exploit a travers le wrapper, le processus exploite — et le cmd.exe qu'il lance — herite du jeton de securite de -crk.

# wrapper.sh — porte le token du bon utilisateur
# cle SSH pre-configuree dans ~/.ssh/id_rsa, login passwordless
ssh -q -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
    -i .ssh/id_rsa app-systeme-ch72-crk@localhost
exit $?

Le shell de connexion de -crk est ch72.exe — la session SSH demarre le binaire vulnerable directement. Le wrapper porte le jeton ; l'exploit traverse le pipe SSH.

Payload & timing

# structure du payload
[ 'A' * 24 ] [ \x00\x10\x40\x00 ] [ \n ]
   padding      give_shell (LE)     termine le lecteur

L'adresse est ecrite en little-endian : 0x00401000 → \x00\x10\x40\x00. Le \n final termine la boucle de lecture pour que main atteigne son ret.

Piege #3 — l'EOF du pipe tue le shell enfant Si l'exploit est envoye via un sous-shell qui se termine aussitot, le bout ecriture du pipe se ferme avant que cmd.exe n'ait fini de demarrer : il voit un EOF immediat sur stdin et sort — on n'obtient que la banniere, aucune commande executee. Un sleep 1 entre le payload et la commande de suivi garde le pipe ouvert le temps que system() spawn le processus. La sequence : Perl ecrit le payload → ch72.exe deborde → ret → give_shell appelle system("cmd.exe") → sleep 1 maintient le pipe pendant le spawn → echo envoie la commande → cmd.exe la lit et l'execute.

Lecons

  • Null bytes dans l'adresse : verifier la condition d'arret exacte du lecteur d'entree — 0x00 passe si le stop est \n/\xff.
  • Boucle de sanitisation bornee : le toupper ne couvre que les 16 premiers octets ; les bytes de l'overflow restent intacts. Lire les bornes dans le desassemblage, pas les supposer.
  • Timing du pipe : quand on chaine « exploit → processus enfant interactif » via un pipe, le bout ecriture doit rester ouvert jusqu'a ce que le processus enfant ait demarre et lise son stdin.
  • Contexte d'execution : un meme payload donne des acces totalement differents selon le jeton utilisateur. Toujours verifier icacls / ACLs pour comprendre qui possede la cible, puis trouver le mecanisme (SUID, wrapper SSH) qui porte le bon token.
  • Pattern Root-Me : les challenges fournissent systematiquement un wrapper.sh ou un binaire SUID qui eleve vers le compte -crk. Le chemin attendu est toujours : exploiter le binaire vulnerable a travers le wrapper, pour que le processus exploite — et tout ce qu'il lance — herite du jeton privilegie.

Pipeline de reverse

Triage : file, entropie, sections — l'entropie elevee, la magie UPX! dans les headers et l'auto-reference /proc/self/exe (le stub de decompression se relit lui-meme) trahissent le packer. strings ne rend que du bruit. Indicateurs hote : /proc/self/status et /proc/self/exe dans les IOCs.
Unpacking : upx -d crackme_packed -o crackme_unpacked — UPX standard, deballage trivial. Le binaire deballe retrouve ses sections completes (.rodata, .plt.sec, .got, .dynsym, .dynstr, etc.) et devient analysable statiquement. Confirmation : file crackme_unpacked montre un ELF normal sans artefact UPX.
Detection de l'anti-debug : dans l'IOC de l'hote, /proc/self/status apparait — signe d'un check TracerPid. Localiser la fonction debugger_present via les xrefs a open → read → strstr. Bypass : patcher le test eax,eax / jnz qui suit pour forcer le chemin propre, ou LD_PRELOAD pour hooker open() et rendre un faux status.
Recuperation des chaines : reperer xprint() (boucle qui XOR un tableau d'octets puis putc), confirmer la cle 0x37, scripter le decodage de tous les blobs de .rodata. Resultat : 7 chaines decodees.
Graphe d'appel : depuis main, isoler les trois fonctions de validation et l'ordre dans lequel elles gardent le chemin « acces accorde ». Ordre : check_format → check_xor_sum → check_hash.

Anti-debug — debugger_present() en detail

Anti-debug — TracerPid via /proc/self/status Ouvre /proc/self/status en lecture via open(O_RDONLY), charge dans un buffer de 2 Ko via read(), puis strstr("TracerPid:") pour localiser la ligne et strtol() pour parser l'entier qui suit. Sous debugger, le noyau ecrit le PID du tracer dans TracerPid (non-zero) et le binaire sort. La chaine "TracerPid:" elle-meme est stockee en clair (pas XOR-encodee) parce qu'elle sert de needle pour strstr — un grep la revelerait. Bypass : patcher le test eax,eax / jnz qui suit pour forcer le chemin propre, ou LD_PRELOAD pour hooker open() et rendre un faux fichier status avec TracerPid:\t0.

Le mecanisme est plus lourd que le ptrace(PTRACE_TRACEME) du crackme #2 : ici le binaire parse le pseudo-filesystem au lieu de s'appuyer sur un seul syscall. La sequence open → read 2 Ko → strstr → strtol est identifiable aux xrefs de ces quatre imports enchaines dans la meme fonction.

Les sept chaines decodees (XOR 0x37)

Obfuscation de chaines — XOR 0x37 Toutes les chaines visibles (banniere, usage, messages de resultat) sont stockees en tableaux d'octets XOR-encodes dans .rodata ; xprint() decode a la volee avant putc(). Un strings naif ne rend rien d'exploitable. Recuperation :
python3 -c "print(''.join(chr(b^0x37) for b in enc))"

Apres decodage de tous les blobs references par xprint(), on obtient les sept chaines du binaire :

#Chaine decodeeOu elle apparait

3Message de debug detecteSi debugger_present() renvoie vrai

La chaine #5 est la branche leurre — elle prouve que les gates ne sont pas purement binaires (tout ou rien) : le binaire distingue « checksum OK, hash KO » de « rien ne passe », ce qui pousse un reverser a croire que le checksum est le seul gate.

Flux d'execution

Le chemin complet a travers main :

; flux d'execution simplifie de main
main()
  → xprint(banner)                    ; decode + affiche la banniere
  → argc == 2 ?                        ; sinon : xprint(usage) → exit(1)
  → debugger_present() ?               ; TracerPid != 0 → xprint(dbg_msg) → exit(1)
  → check_format(argv[1])              ; strlen==9, [4]=='-', [A-Z0-9]
  → check_xor_sum(argv[1])             ; even ^ odd == 0x2F
  → check_hash(argv[1])                ; feistel_hash == 0x8FCDA6FB
       ; si checksum OK mais hash KO → "Almost... not quite." (LEURRE)
       ; si tout KO → "Wrong key."
       ; si tout OK → "Access granted. Welcome!"

Feistel hash — structure interne

; feistel_hash(key8) — hash maison, 4 rounds sur 8 octets (32 iterations)
L = 0xCAFEBABE
R = 0xDEADC0DE
for round in 0..3:
    for i in 0..7:
        f   = (R ^ (key[i] * 0x9E3779B9)) + round   ; golden ratio constant
        f   = rotl32(f, 13)
        tmp = L ^ f
        L   = R
        R   = tmp
return L ^ R                                  ; cible : 0x8FCDA6FB

Le multiplicateur 0x9E3779B9 est la constante du nombre d'or (famille FNV/Murmur) — un choix classique pour disperser les bits. rotl32(f, 13) assure le melange non-lineaire. Le hash final est L ^ R apres 32 iterations.

Keygen — espace de recherche

L'espace brut est [A-Z0-9]^8 = 36^8 ≈ 2,8 × 10^12 — trop grand pour un brute-force naif. La strategie est un filtre en deux temps :

  1. Filtre rapide par checksum : evaluer even_sum ^ odd_sum == 0x2F ne coute que 8 additions et un XOR. Seule une fraction de l'espace passe — les candidats restants sont beaucoup moins nombreux.
  2. Validation par hash : sur les candidats survivants, calculer feistel_hash(key8) (32 iterations) et comparer a 0x8FCDA6FB.
Piege — la branche leurre Si le checksum (etape 2) passe mais que le hash Feistel echoue, le binaire affiche "Almost... not quite." au lieu de "Wrong key.". C'est delibere : ca pousse le reverser a croire que le checksum est le seul gate et a s'acharner dessus, alors que le vrai verrou est le hash. Un reverser presse livre une « solution » qui satisfait seulement l'etape 2 — et ne comprend pas pourquoi elle ne marche pas.

Le keygen brute-force l'espace des 8 caracteres [A-Z0-9] filtre d'abord par le checksum 0x2F (rapide), puis valide par feistel_hash == 0x8FCDA6FB. La cle tombe :

Cle valide FLAG-CTFX

Verification : 9 caracteres, tiret en position 4, alphanumerique majuscule — (F+A+G+X) ^ (L+C+F+T) = 0x2F — feistel_hash("FLAGCTFX") = 0x8FCDA6FB.

Cote conception — pourquoi quatre couches ? Chaque couche s'adresse a un profil de reverser : le packing UPX bloque le debutant qui n'a que strings. Le XOR 0x37 arrete celui qui deballe mais ne sait pas scripter. L'anti-debug punit le reflexe « je lance sous gdb d'abord ». Et la branche leurre piege l'intermediaire qui trouve le checksum et s'arrete la. Seul le parcours complet — deballer, decoder, identifier les trois gates, reverser le hash — mene a la cle. Concevoir cette graduation est en soi un exercice de design.

Anti-debug — PTRACE_TRACEME

Toute premiere action de main, avant meme le prompt : le processus se met lui-meme sous trace. Un processus n'ayant qu'un seul tracer possible, si gdb/strace/ltrace est deja attache, le noyau renvoie -EPERM et le wrapper libc rend -1.

0x40118e  mov    ecx, 0          ; arg4 = 0
0x401193  mov    edx, 0          ; arg3 = 0 (addr)
0x401198  mov    esi, 0          ; arg2 = 0 (pid, ignore)
0x40119d  mov    edi, 0          ; arg1 = 0 = PTRACE_TRACEME
0x4011a2  mov    eax, 0
0x4011a7  call   0x401080        ; ptrace@plt
0x4011ac  cmp    rax, -1         ; deja trace ?
0x4011b0  jne    0x4011bc        ; non → continue vers le prompt
0x4011b2  mov    eax, 0          ; oui → return 0
0x4011b7  jmp    0x4012dd        ; → leave; ret (exit silencieux)
Le tell est une absence Sous debugger, le binaire sort avec le code 0 avant d'afficher "Enter the flag: " — pas de banniere « je t'ai detecte », pas de SIGTRAP, rien. Le signal le plus utile est l'absence de prompt : le reflexe « je le lance juste sous gdb » est puni par un binaire qui a l'air casse. Bypass : transformer le jne en jmp inconditionnel, patcher cmp rax,-1 en -2, ou LD_PRELOAD un stub ptrace qui rend 0.

Le premier argument (edi = 0) est la valeur PTRACE_TRACEME de l'enum __ptrace_request. Quand un processus l'invoque, le noyau le marque comme etant trace par son parent. Un processus ne peut avoir qu'un seul tracer ; si un debugger est deja attache, le noyau renvoie -EPERM et le wrapper libc retourne -1. Le cmp rax, -1 suivi du jne branche par-dessus un return 0 immediat — sous debugger, le binaire sort silencieusement avec le code 0.

Code source complet — crackme-v2.c

Puisque c'est un crackme que j'ai ecrit, voici le source complet (le binaire est compile a partir de ce fichier exact) :

/* crackme-v2.c — source complet */
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/ptrace.h>

int main(int argc, char *argv[]) {
    // Anti-debug: ptrace TRACEME
    if (ptrace(PTRACE_TRACEME, 0, NULL, NULL) == -1) {
        // EPERM or other failure — exit silently
        return 0;
    }

    printf("Enter the flag: ");
    char input[128];
    if (!fgets(input, sizeof(input), stdin)) {
        return 1;
    }
    // strip newline
    input[strcspn(input, "\n")] = '\0';

    unsigned char encoded[22] = {
        0x24, 0x2E, 0x23, 0x25, 0x39, 0x20, 0x76, 0x20,
        0x3B, 0x30, 0x27, 0x34, 0x21, 0x2A, 0x76, 0x2E,
        0x2E, 0x70, 0x72, 0x70, 0x76, 0x3F
    };

    if (strlen(input) != 22) {
        puts("Wrong.");
        return 1;
    }

    for (int i = 0; i < 22; i++) {
        if ((input[i] ^ 0x42) != encoded[i]) {
            puts("Wrong.");
            return 1;
        }
    }

    puts("Correct!");
    return 0;
}

La contrainte de conception : aucun flag{ en clair dans .rodata — verifie par strings crackme-v2 | grep 'flag{' au build. La cle 0x42 apparait directement dans l'instruction xor eax, 0x42 du binaire compile — c'est voulu pour la solvabilite.

Sequence d'entree dans le desassemblage

Apres le check anti-debug, main enchaine la lecture et le pre-traitement de l'input. La sequence fgets → strcspn → strlen est directement lisible dans le desassemblage :

; lecture de l'input
0x4011bc  lea    rax, [rip+0xe41]         ; "Enter the flag: "
0x4011c3  mov    rdi, rax
0x4011c6  mov    eax, 0
0x4011cb  call   0x401060                ; printf@plt

; fgets(input, 0x80, stdin)
0x4011d0  mov    rdx, QWORD PTR [rip+0x2e59]  ; stdin
0x4011d7  lea    rax, [rbp-0x90]          ; input buffer
0x4011de  mov    esi, 0x80                ; max 128 octets
0x4011e3  mov    rdi, rax
0x4011e6  call   0x401070                ; fgets@plt

; strip newline : input[strcspn(input, "\n")] = '\0'
0x4011f1  lea    rax, [rbp-0x90]
0x4011f8  lea    rdx, [rip+0xe0a]         ; "\n"
0x4011ff  mov    rsi, rdx
0x401202  mov    rdi, rax
0x401205  call   0x401050                ; strcspn@plt
0x40120a  mov    BYTE PTR [rbp+rax-0x90], 0   ; termine la chaine

; gate de longueur
0x40120f  lea    rax, [rbp-0x90]
0x401216  call   0x401040                ; strlen@plt
0x40121b  cmp    rax, 0x16                ; strlen == 22 ?
0x40121f  je     0x401237                ; oui → continue

Le buffer d'input se situe a [rbp-0x90] (144 octets reserves, seuls 128 utilises par fgets). Le strcspn avec "\n" comme jeu de rejet renvoie l'index du premier newline, que main ecrase avec un null byte pour terminer la chaine.

Le ciphertext est inline, pas dans .rodata

Apres le gate de longueur, main materialise les 22 octets attendus en immediats via trois movabs — il n'y a aucun blob a grepper dans .rodata :

0x40121b  movabs rax, 0x2076203925232e24   ; octets 0..7
0x401225  movabs rdx, 0x2e762a213427303b   ; octets 8..15
0x40122f  mov    [rbp-0xb0], rax          ; store 0..7
0x401236  mov    [rbp-0xa8], rdx          ; store 8..15
0x40123d  movabs rax, 0x3f767072702e2e76   ; octets 14..21
0x401247  mov    [rbp-0xa2], rax          ; store 14..21 — CHEVAUCHE les 2 derniers !
Piege de lecture — le chevauchement Le troisieme store vise rbp-0xa2 = (rbp-0xb0) + 14 : il recouvre volontairement les 2 derniers octets (0x2e 0x76) du second qword pour placer les 8 octets finaux sans ecrire un 6-octets a part. Les deux ecritures sont identiques au recouvrement, donc la mise en page finale est non ambigue — mais qui lit le buffer lineairement sans faire le depliage little-endian se trompe. Octets bruts obtenus :
242e2325392076203b302734212a762e2e707270763f

Ces memes octets sont aussi visibles a strings comme les fragments $.#%9 v / ;0'4!*v. / v..prpv? — utile pour reperer le cipher avant meme de desassembler.

La cle XOR — boucle de verification complete

La boucle de verification itere i = 0..0x15 (22 tours, coherent avec le gate strlen == 0x16 juste au-dessus) et compare input[i] ^ 0x42 a expected[i] :

0x401279  mov    DWORD PTR [rbp-4], 0     ; i = 0
0x401280  jmp    0x4012c3                ; → test de boucle
0x401282  mov    eax, [rbp-4]             ; eax = i
0x401285  cdqe                             ; sign-extend eax → rax
0x401287  movzx  eax, BYTE PTR [rbp+rax-0x90]  ; input[i]
0x40128f  xor    eax, 0x42                ; CLE = 0x42
0x401292  movsx  edx, al                  ; sign-extend byte → dword
0x401295  mov    eax, [rbp-4]             ; eax = i (recharge)
0x401298  cdqe                             ; sign-extend pour adressage
0x40129a  movzx  eax, BYTE PTR [rbp+rax-0xb0]  ; expected[i]
0x4012a2  movzx  eax, al                  ; zero-extend byte
0x4012a5  cmp    edx, eax                 ; input[i]^0x42 == expected[i] ?
0x4012a7  je     0x4012bf                ; match → iteration suivante
0x4012a9  lea    rax, [rip+0xd67]         ; "Wrong."  → puts, return 1
0x4012b0  mov    rdi, rax
0x4012b3  call   0x401030                ; puts@plt
0x4012b8  mov    eax, 1                   ; return code 1
0x4012bd  jmp    0x4012dd                ; → leave; ret
0x4012bf  add    DWORD PTR [rbp-4], 1     ; i++
0x4012c3  cmp    DWORD PTR [rbp-4], 0x15  ; i <= 21 ? → boucle
0x4012c7  jle    0x401282                ; oui → iteration
0x4012c9  lea    rax, [rip+0xd4e]         ; "Correct!"
0x4012d0  mov    rdi, rax
0x4012d3  call   0x401030                ; puts@plt
0x4012d8  mov    eax, 0                   ; return code 0

Cle constante, mono-octet, aucun salt par position : XOR etant son propre inverse, la recuperation est un one-liner. A noter les deux cdqe (sign-extend eax → rax) generes par -O0 pour l'adressage 64 bits — artefact typique de la compilation non optimisee, chaque acces a i recharge la variable locale et la sign-extend au lieu d'utiliser un registre.

python3 -c "print(bytes(b^0x42 for b in bytes.fromhex('242e2325392076203b302734212a762e2e707270763f')).decode())"
# → flag{b4byrevch4ll2024}
Flag flag{b4byrevch4ll2024}

Verifie contre le binaire : entree correcte → Enter the flag: Correct! (rc=0) ; controle negatif wrong → Wrong. (rc=1) — pour prouver que la boucle se declenche vraiment et qu'on ne lit pas un chemin mort.

Ce qui rend le challenge non-trivial pour un debutant

Malgre sa difficulte 2/5, deux pieges ralentissent le debutant :

  • Pas de flag en clair : un strings crackme-v2 | grep flag{ naif ne rend rien. Les 22 octets attendus sont materialises en immediats dans trois movabs — pas en .rodata. Il faut lire le desassemblage de main, pas grepper le binaire.
  • Le chevauchement des stores : les trois movabs / mov qui materialisent le ciphertext se chevauchent de 2 octets (le troisieme store a rbp-0xa2 recouvre les positions 14-15 du second). Qui lit le buffer lineairement sans depliage little-endian obtient un ciphertext errone.
  • Exit silencieux sous debugger : le PTRACE_TRACEME fait sortir le binaire avec code 0 avant le prompt. Le debutant qui lance sous gdb voit un binaire qui « ne fait rien » et ne pense pas a chercher un anti-debug.
Cote conception — la QA a rattrape des erreurs Concevoir un crackme demande sa propre discipline. La specification initiale du plan annoncait 21 caracteres au lieu de 22 (le flag flag{b4byrevch4ll2024} fait 22 octets, pas 21), et le blob encode contenait des octets hallucines — un calcul XOR fait a la main qui ne correspondait pas au vrai 0x42 du flag. Un document de corrections a recalcule le blob correct (24 2E 23 25 39 20 76 20 3B 30 27 34 21 2A 76 2E 2E 70 72 70 76 3F, 22 octets), corrige les bornes strlen == 22 / boucle i < 22, et defini trois tests de build obligatoires : 
# tests de build (les trois doivent passer)
strings crackme-v2 | grep -q 'flag{' && echo "FAIL: plaintext leak" || echo "OK: no leak"
echo 'flag{b4byrevch4ll2024}' | ./crackme-v2     # doit afficher "Correct!"
echo 'flag{wrong_flag_value}' | ./crackme-v2     # doit afficher "Wrong."

Si l'un echoue, le binaire est casse — on corrige et on reteste. La rigueur du build est aussi importante que la rigueur du reverse : un blob encode errone rend le crackme insoluble, et un flag en clair dans .rodata le rend trivial.

Deux anti-debug, deux philosophies Le crackme #1 parse /proc/self/status (quatre appels : open → read → strstr → strtol) — un mecanisme lourd, identifiable par les xrefs aux fonctions I/O. Le crackme #2 appelle ptrace(PTRACE_TRACEME) — un seul syscall, plus discret, mais aussi plus facile a patcher (un seul jne a transformer). Le gradient de difficulte est delibere : le #2 sert d'entree de gamme, le #1 monte la marche avec quatre couches empilees. Concevoir les deux a permis de calibrer la difficulte perceptive — ce qui bloque un debutant vs. ce qui bloque un intermediaire.

03b Laboratoire anti-analyse — crackmes experts concus et resolus

Au-dela des deux crackmes detailles ci-dessus, j'ai construit et resolu un laboratoire de crackmes « expert » dedie aux techniques anti-analyse — concus d'abord, casses ensuite, comme les deux precedents. Chaque binaire implemente une technique de detection reelle (celles utilisees par les packers et les malwares), chaque detection est reactive : etre detecte ne fait pas seulement sortir — ca corrompt la cle de decryption en memoire, si bien que meme le bon mot de passe affiche FAIL.

Pourquoi concevoir ces defenses change la facon de les contourner

  • La reactivite change tout : un anti-debug qui exit() se NOP en deux instructions. Un anti-debug qui corrupte sa propre cle avant le compare force l'analyste a patcher avant que la detection ne tourne — pas apres. C'est le pattern if (debugger) key ^= 0xFF; vs. if (debugger) exit(1); — le premier est trivial a contourner, le second exige de comprendre l'ordre des operations.
  • La source du signal fait la difference : TracerPid vient de /proc (hookable par LD_PRELOAD sur open), DR6 vient de ptrace (pas hookable — c'est un syscall), le timing vDSO ne passe ni libc ni syscall visible. Chaque couche supprime une famille de bypass.
  • Le processus enfant comme cache-cle : stocker une partie du secret dans un process separe via memoire partagee rend l'analyse mono-processus (gdb par defaut) aveugle — le secret n'existe pas dans l'espace d'adresse observe.
  • Seccomp retourne l'arme : le meme filtre qu'un sandboxing defensif utilise pour restreindre un process sert ici a interdire au debugger ses syscalls de tracing. Une defense n'est pas defensive par nature — c'est la position qui decide.
Cadre Lab prive sur ma machine : binaires concus par moi, resolus par moi, sources dans le repo du lab pour verifier le ground truth apres chaque solve. Techniques inspirees de l'analyse de malwares reels — utilisees ici dans un contexte d'apprentissage et de conception de challenges, pas de distribution.

Resoudre et concevoir des challenges, c'est un versant ; les heberger proprement en est un autre. Hexgate est le backend d'une petite plateforme CTF que j'ai concu : une application FastAPI mono-conteneur (port 8080), SQLite en persistance, sans frontend — API JSON pure. C'est un projet distinct du travail de resolution ci-dessus, et je le presente comme tel : ici je porte la casquette « plateforme », pas « solveur ».

Modele de donnees — SQLModel

Quatre tables couvrent l'ensemble du domaine : utilisateurs, challenges, solves, et le journal de tentatives :

Flux d'authentification

  1. Register : bcrypt(password, cost=12) → insert en base → retourne {id, username, email}.
  2. Login : verifie le hash bcrypt → emet un JWT HS256 (exp 24 h, claims : sub, username, is_admin).
  3. Routes protegees : dependance get_current_user decode le JWT depuis Authorization: Bearer <token>, fetch le User en base, l'injecte dans le handler.
  4. Routes admin : verifie is_admin dans le token ou le header x-admin-key correspondant a ADMIN_KEY — double voie pour l'administration programmatique sans session.

Rate-limit — fenetre glissante en memoire

Le rate-limiter est un dict[tuple[int, int], deque[float]] en memoire, cle par (user_id, challenge_id). A chaque soumission :

  1. Purger les timestamps plus vieux que 60 secondes du deque.
  2. Si len(deque) >= 5 → lever HTTPException(429).
  3. Sinon, appender le timestamp courant et laisser passer.

Le limiter est non partage entre workers et s'efface au redemarrage — acceptable pour un mini-CTF, mais l'architecture impose --workers 1 dans le Dockerfile. Si un horizontal scaling est un jour necessaire, la couche de stockage se remplacerait par un Redis-backed limiter sans changer l'interface.

Threat model livre avec Comme pour tout ce que je construis, j'ai passe le design au fil du threat modeling. Points saillants :
  1. Side-channel temporel sur les flags : comparaison de flag en temps constant (secrets.compare_digest / bcrypt) pour eviter la fuite par timing. Une comparaison == naive stopperait au premier octet different, laissant filtrer la position correcte.
  2. Rate-limit non-HA : en memoire, non partage entre workers, reset au redemarrage → imposer --workers 1 et documenter le caractere non-HA. Un multi-process uvicorn contournerait la limite.
  3. Secrets rotatifs : JWT_SECRET et ADMIN_KEY forts, rotables. Si le JWT leake, les tokens peuvent etre forges — d'ou rotation periodique (provoque un logout de tous les users).
  4. Pepper sur le hash de flag : FLAG_PEPPER (variable d'env) concatene au flag avant hachage. Bloque le pre-calcul : meme en cas de fuite de la base, les hashes de flag ne sont pas inversibles sans le pepper.
  5. Path traversal sur les uploads : validation des noms de fichiers uploadees contre le ../. Les fichiers sont stockes hors du web root et servis via un endpoint controle.
  6. Pas de stack traces en prod : debug=False. Les erreurs de validation FastAPI incluent les noms de champs mais jamais de traceback.
  7. SQLite concurrence : SQLite gere bien les lecteurs multiples mais les ecritures concurrentes peuvent bloquer. Mode WAL active pour reduire le verrouillage ; les ecritures sont gardees courtes.
  8. SQL injection : SQLModel utilise des requetes parametrees, ce qui mitigue l'injection SQL standard. Les endpoints admin qui construisent des requetes d'audit utilisent des parametres lies, jamais de f-strings.
  9. Abus d'inscription : pas de verification d'email / captcha a l'inscription — ouvert a la creation massive de comptes pour manipulation du score. Documente comme risque hors scope du mini-CTF mais note dans l'audit.
  10. Choix du hash de flag : SHA-256 avec pepper est rapide et suffisant pour la comparaison de flags ; bcrypt offrirait une meilleure resistance au brute-force mais au prix de la latence. Le choix retenu est SHA-256 + pepper, avec secrets.compare_digest pour la comparaison en temps constant.

Scoreboard — requete de classement

Le classement global est calcule par une seule requete, ordonnee par points decroissants puis par horodatage du dernier solve (premier a atteindre le score gagne le departage) :

SELECT user_id,
       SUM(points)  AS total,
       COUNT(*)     AS solves
FROM   solves
GROUP BY user_id
ORDER BY total DESC, solved_at ASC

Le endpoint /scoreboard est public (pas de JWT requis) — le classement est visible par tous. Le endpoint /scoreboard/me (JWT requis) retourne le rang et les stats du joueur courant.

Bilan

  • Exploitation binaire : lecture de pile, contournement d'absence de protections, ret2win — et surtout la partie souvent oubliee : porter le bon jeton d'acces (le wrapper SSH) et gerer le timing du pipe pour ne pas perdre le shell.
  • Anti-protection : de-packing UPX, defaite d'anti-debug (/proc/self/status TracerPid via open/read/strstr/strtol, PTRACE_TRACEME via un seul syscall), desobfuscation de chaines XOR, reverse d'un hash Feistel maison, et reperage d'une branche leurre.
  • Producteur autant que solveur : je concois mes propres crackmes (design des couches de defense, choix des constantes, QA du ciphertext — y compris la correction d'un blob encode hallucine et d'une erreur de longueur dans la spec, verification des bornes et des blobs encodes par trois tests de build automatises) puis je les casse a froid.
